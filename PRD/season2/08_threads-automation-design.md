# 스레드(Threads) 자동화 설계 초안

> 시즌2 P0 #9. 블로그와 짝이지만 구조가 완전히 다름 — 메타 공식 API가 있어 **서버에서 처리(설치 도우미 불필요)**.
> ⚠️ Threads API 세부(한도·권한·필드)는 개발 착수 시 developers.facebook.com/docs/threads 최신본 재확인.

---

## 1. 블로그와 결정적 차이

| 항목 | 네이버 블로그 | 스레드 |
|------|--------------|--------|
| 공식 API | 없음 → 브라우저 자동화(카무폭스) 필요 | **있음(Meta Threads API)** |
| 처리 위치 | 사용자 PC 발행 도우미 | **우리 서버**(설치 불필요) |
| 계정 연동 | 도우미 안에서 네이버 로그인 | **OAuth 연동 + 메타 앱 심사** |
| 예약 | 네이버 자체 예약 기능 | **우리 서버 스케줄러가 예약 시각에 API 호출** |
| 글 길이 | 길다(1800~2500자) | 짧다(**최대 500자**) |

→ 스레드는 서버에서 깔끔하게 처리. 블로그의 IP·설치 문제 없음.

## 2. 사용자 흐름

```
[최초 1회] 마이페이지에서 "스레드 계정 연동"(Meta OAuth 로그인 → 권한 허용)
   ↓
[반복]
① 주제/키워드 or 발행한 블로그 글 선택
② 스레드용 짧은 글 생성(500자, 아래 프롬프트) + 이미지(선택)
③ 규제 검수(04번) 통과
④ 게시 방식 선택: 즉시 게시 / 예약 게시
⑤ 서버가 Threads API로 게시(예약이면 스케줄러가 그 시각에)
```

## 3. 기술 요소

- **인증**: Meta 앱 생성 → `threads_basic`, `threads_content_publish` 권한 → OAuth로 사용자 스레드 계정 연동. **프로덕션은 메타 앱 심사 필요(미결 #6, 소요기간 확인).**
- **게시**: Threads API 2단계 — ①미디어 컨테이너 생성 ②publish. 텍스트/이미지/동영상 지원.
- **예약**: Threads API에 네이티브 예약 없음 → 우리 서버가 예약 레코드 저장 후 크론/큐로 그 시각에 게시. (블로그 도우미와 달리 서버라 사용자 PC 무관 = 예약 안정적)
- **한도**: 사용자당 24시간 게시 한도 있음(대략 250건/일 수준) — 우리 사용량(하루 몇 건)엔 여유. 초과 시 큐 대기.
- **이미지**: 스레드는 정사각/세로 선호 → gpt-image-2 정사각(1024×1024) 재활용 가능.

## 4. 스레드용 글 생성 프롬프트 (짧은 글 전용)

```
너는 스레드(Threads)용 짧은 글을 쓴다. 최대 500자, 1~3문단.
목표: {{키워드/주제}}로 스레드 피드에서 눈길을 끌고, 저장·공유·프로필 방문을 유도.
업종: {{업종}} · 페르소나: {{페르소나}}

# 규칙
- 첫 문장이 후킹(질문·의외·공감). 스레드는 첫 줄이 전부.
- 짧고 리듬감 있게. 줄바꿈 활용. 이모지는 0~2개.
- 해시태그 0~3개(스레드는 과다 해시태그 역효과).
- 링크·연락처 직접 노출보다 "프로필에서" 유도.
- 병원·변호사: 규제 동일 적용(승소·완치·최상급 금지). CTA는 유인 아닌 안내.

# 입력 소스 2가지
(A) 주제/키워드에서 새로 작성
(B) 발행한 블로그 글 → 핵심 1개만 뽑아 스레드용으로 요약·변환 (P1 기능 #14)

# 출력
스레드 본문(500자 이내) + 이미지 마커(선택) + 해시태그.
※ 규제 검수는 생성 후 04번 패스가 수행.
```

## 5. 공통 모듈 적용

- **규제 검수(04번)**: 병원·변호사는 스레드에도 광고규제 적용 → 동일 통과.
- **AEO(05번)**: 스레드는 짧아 AEO 약하게 — 핵심 즉답 1문장만. FAQ·표 없음.
- **AI 인용 규칙(04번 6장)**: 근거 없는 수치·주장 금지 동일.

## 6. 미결 / 확인

| 항목 | 내용 |
|------|------|
| 메타 앱 심사 기간 | `threads_content_publish` 프로덕션 승인 소요(미결 #6) |
| 블로그→스레드 변환 | P1 #14로 이미 계획. 우선순위: 스레드 신규작성(P0) → 변환(P1) |
| 예약 스케줄러 | 블로그(네이버 예약)와 스레드(서버 예약) 방식이 달라 UI에서 통합 표시 필요 |
| 동영상·다중이미지 | 1차는 텍스트+이미지1장. 캐러셀·영상은 후순위 |

## 6-1. 메타 API 변경 대응 (미비점 수정)
- API 버전을 고정해 호출하고, 메타 개발자 공지·changelog를 주기 모니터링.
- 게시 실패 시 자동 재시도 + 사용자·운영자 알림. 권한 변경으로 게시 막히면 재연동 유도.
- 블로그 발행 도우미의 자동 업데이트 개념을 서버측 API 어댑터에도 적용(변경 시 어댑터만 교체).

## 7. 요약

스레드는 서버에서 공식 API로 처리 → 블로그보다 기술적으로 깔끔. 최대 리스크는 **메타 앱 심사 기간**(개발과 병행 착수). 글 생성·규제·이미지는 블로그 파이프라인 재활용.
