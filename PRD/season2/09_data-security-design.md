# 데이터 보안·개인정보 설계 (🔴 최우선)

> 8-1장 #1 해결 설계. 병원·변호사 타깃이라 업로드 자료에 **진료정보·사건자료** 등 민감·기밀이 섞일 수 있음. 이걸 외부 AI로 보내는 구조라 개인정보보호법 + 변호사 비밀유지의무 리스크.
> 목표: "민감정보가 애초에 안 들어오게 + 들어와도 안전하게 + 법적 방어선".

---

## 1. 리스크 3층

| 층 | 무엇 | 위험 |
|----|------|------|
| 입력 | 사용자가 진료기록·사건기록·고객 개인정보를 업로드 | 처음부터 민감정보 유입 |
| 처리 | 그 내용을 외부 AI API(Claude·OpenAI)로 전송 | 제3자 전송·학습·보관 |
| 저장 | 업로드 자료·생성 글을 우리 서버에 보관 | 유출 시 대량 피해 |

## 2. 대응 설계 (층별)

### A. 입력 단계 — 민감정보 유입 차단
- **업로드 시 명확 안내**: "환자 실명·주민번호·진료기록, 의뢰인 실명·사건번호 등 개인·기밀 정보는 올리지 마세요. 글쓰기 근거용 일반 자료만."
- **자동 마스킹 스캐너(권장)**: 업로드·생성 텍스트에서 주민번호·전화·계좌·이메일·실명 패턴 감지 → 자동 가림 또는 경고. (정규식 + 개인정보 패턴)
- 업로드 자료는 "참고 근거"로만 쓰고, 그 원문이 발행 글에 복붙되지 않게(인용 규칙과 연동).

### B. 처리 단계 — 외부 AI 전송 안전
- **AI API 무학습·무보관(ZDR) 옵션 사용**: Claude/OpenAI의 데이터 미학습·zero-retention 설정 또는 기업 계약으로 전송 데이터가 학습·장기보관되지 않게. (계약·설정 확인 = 미결)
- 전송 전 마스킹 적용본만 보냄.
- 로그에 원문 저장 최소화(디버그 로그에 사용자 자료 남기지 않기).

### C. 저장 단계 — 서버 보안
- 업로드 자료·페르소나·생성 글 **암호화 저장**(at-rest 암호화).
- 접근 통제(운영자도 함부로 못 봄), 접근 로그.
- **보관기간 정책**: 사용권 만료 후 N개월 보관 → 자동 삭제(만료 데이터 정책과 연동). 사용자 요청 시 즉시 삭제.
- 네이버 로그인 정보는 **서버 미보관**(발행 도우미가 사용자 PC에만) — 이미 확정. 도우미 내 저장도 OS 보안저장소 사용.

## 3. 법적 방어선 (약관·방침)
- **개인정보처리방침** 신설: 무엇을 받고, 외부 AI로 보내고, 얼마나 보관하고, 어떻게 파기하는지 명시.
- **약관에 데이터 조항**: "민감·기밀 정보 업로드 금지, 위반 시 책임은 사용자" + "필요 처리 위해 외부 AI에 전송됨을 동의".
- 변호사 대상: 사건 자료는 비밀유지의무 대상 → "의뢰인 식별정보 제거 후 사용" 안내를 온보딩에 강조.
- 07번(면책)과 한 세트로 변호사 감수.

## 4. 우선순위
- 🔴 출시 전 필수: A의 안내문구 + B의 AI 무학습·무보관 설정 + C의 암호화·삭제정책 + 개인정보처리방침.
- 🟡 권장: A의 자동 마스킹 스캐너(초기엔 안내+수동, 이후 자동화).

## 5. 미결
- Claude/OpenAI의 무학습·무보관(ZDR) 계약·설정 실제 가능 여부·조건 확인.
- 자동 마스킹 스캐너 1차 범위(정규식 수준 vs AI 검출).
- 데이터 보관기간 숫자(만료 후 몇 개월).
