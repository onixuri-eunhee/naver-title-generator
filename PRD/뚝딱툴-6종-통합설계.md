# 뚝딱툴 6종 생성기 — 통합 설계안 v1 (fable 재검토 반영 · 2026-07-07)

> 목적: 6개 생성기(블로그·이미지·스레드·카드뉴스·숏폼·롱폼)의
> "다듬은 스킬 레시피"를 사이트에 어떻게 앉힐지 최종 확정.
> fable5 창(~7/8 14:00)은 **골드샘플(품질 기준 문장) 대량 생산**에 쓴다 — Sonnet 프롬프트 few-shot 재료(0-2b).

## Part 0. 핵심 결론 (먼저 읽기)

### 0-0. 🎯 북극성 목표 (모든 설계 판단 기준)
이 제품의 목표는 예쁜 생성물이 아니라 **① 목적에 맞는 콘텐츠 발행 → ② 검색 상위노출 → ③ 홈판(홈피드) 노출.**
모든 생성기·기능은 "이게 상위노출/홈판노출로 이어지나?"로 평가한다.

**⚠️ 중요한 사실: 상위노출·홈판노출은 사이트가 아니라 "네이버에서, 발행된 뒤" 일어난다.**
사이트의 콘텐츠 생성은 필요조건일 뿐 충분조건이 아니다. 노출을 실제로 만드는 요인:

| 목표 | 무엇이 만드나 (드라이버) | 사이트 몫(생성) | 발행 몫(PC 도우미·전략) |
|---|---|---|---|
| **목적적합 콘텐츠** | 키워드 미끼라도 본문은 타겟 각도·페인포인트 | ✅ 레시피 | — |
| **검색 상위노출** | 키워드 타겟 · 정보완결·체류시간 · 채널 주제 전문성(C-Rank) · 저품질 회피 · 태그/내부링크 | ✅ 생성이 절반 | ✅ 규칙적·분산 발행, 카테고리 일관, 재발행 관리 = 절반 |
| **홈판 노출** | 후킹 제목·첫3줄 · 클릭·체류·공감 반응 · 주제 일관성 · 규칙 발행 | ✅ 제목·훅·구조 | ✅ 발행 타이밍 분산·주제 일관 = 절반 |

→ **결론: 생성(사이트)만 잘해선 노출 안 된다. 발행 전략(규칙성·분산·주제 일관)+발행 도우미가 나머지 절반.**
   설계는 두 몫을 다 커버해야 한다. 각 생성기 섹션에 "상위노출/홈판 기여" 축을 명시한다.

### 0-1. 무엇이 문제였나
- 사이트 6개 생성기의 결과물이 아쉬웠던 진짜 이유 = **사이트가 옛 레시피를 쓰고 있어서.**
- 그동안 대표가 스킬(`blog-publisher-v2` 등)에서 프롬프트·규칙을 계속 다듬었지만,
  그 발전이 사이트 코드(`lib/*.js`)에는 반영되지 않았다. 모델·재구성 문제가 아니다.

### 0-2. 그래서 방향 (재구성 아님, 이식임)
- **사이트를 fable로 통째로 재구성하지 않는다.** 할 일 = 스킬의 완성 레시피를 사이트 서버 코드로 이식.

### 0-2b. 🎯 모델 전략 확정 (2026-07-07 대표)
- **뚝딱툴(양산) = Sonnet 5.** 전문가용(병의원·변호사, 시즌2) = **Opus.**
- **fable5 = 양산 모델 아님 → "품질 기준(레퍼런스)".**
- 방법: fable5로 **골드 샘플** 생성(마감 창 활용) → 그 수준이 나오도록 **Sonnet 작업 프롬프트를 튜닝**(fable 문장을 few-shot 예시로 심고, Sonnet이 흘리는 제약을 하드하게). 양산은 Sonnet, 품질은 fable급.

### 0-2c. 🚨 탈개인화 원칙 (뚝딱툴 = 여러 사람 SaaS · 2026-07-07 대표)
- 다듬은 스킬은 **대표 개인용**이라 실적·서사·USP가 하드코딩돼 있음(예: "14년 차·계약률 90%·코칭 200명·하루 10편").
- 뚝딱툴은 **여러 사용자**가 씀 → 이 개인 정보를 프롬프트에 넣으면 안 됨.
- **이식 = 사람을 벗기고 구조만 남긴다.** 모든 개인 실적·경험·서사·USP는 **사용자 입력 슬롯**(마이페이지 세팅 + 글쓰기 "추가란")으로 치환.
  - 8실적권위·본인서사·실제사례 패턴 → **사용자가 추가란에 넣은 값이 있을 때만** 그 값으로. 없으면 그 패턴 생략(날조 금지).
- (시즌2 `lib/season2`의 persona/references 슬롯과 동일 구조 = 뚝딱툴에도 적용.)

### 0-3. 모든 생성기는 두 층으로 쪼갠다
| 층 | 내용 | 어디로 |
|---|---|---|
| **레시피 층** | 프롬프트·규칙·구조·체크리스트 | ✅ 사이트 서버로 이식 가능 |
| **로컬 실행 층** | 카무폭스 발행·PC 이미지 스크립트·디스크 wiki/PDF | ❌ 사이트 불가 → PC 발행 도우미 또는 스킬로 유지 |

→ 사이트가 담당: 원고·이미지·대본 **생성**(레시피 층).
→ PC 도우미/스킬이 담당: 네이버 **발행**, 로컬 자료 반영(로컬 층).

### 0-4. 순서 (마감 활용)
1. **설계 확정** ✅ (v1 완료)
2. **fable5 골드샘플 뱅크 생산** (마감 창 — 훅·제목·첫문장·스레드 첫줄·영상 3초훅)
3. 사이트 서버 이식: 훅엔진 → 블로그+이미지(P0) → 스레드(P1) → 영상(P2) → 카드뉴스+캐러셀(P3)
4. ~~모델 선정~~ → 확정됨(0-2b): 뚝딱툴=Sonnet / 전문가=Opus / fable=기준

## Part 1. 블로그 생성기

### 1-1. 현재 스킬 레시피 (blog-publisher-v2, v2.3 · 매우 성숙)
- **키워드**: 네이버 검색광고 API → 유입용(넓은) 1~2 + 전환용(니치) 1 섞기. 넓은 키워드는 미끼, 본문은 타겟 각도 고정.
- **제목**: 12패턴(구체숫자·타겟호명·결과약속·실수경고·반전·질문·리스트·실적권위·공통점경고·의심하라·손실프레이밍·VS비교) + 장치 쌓기(말줄임표·따옴표훅·호기심갭). 25자·2~3개 결합. 부정 어그로("망해요") 금지.
- **첫문장**: 8종 오프닝 뱅크(권위·공감YES·따옴표·충격숫자·손해경고·장면·통념뒤집기·반문). 배치 내 유형 안 겹치게(저품질 방지).
- **본문**: 4단 구조(도입훅→잘못된선택→기준제시+실제사례→CTA). 2,000~3,000자. -요/-니다체. 금지어(방법/꿀팁/비법/하세요).
- **품질 게이트**: AI감지 16항목×10점, 112점 이상 통과.
- **AEO**: 결론 먼저·경험 문단 필수·출처/URL 금지·마무리 3줄 요약.

### 1-2. 왜 결과가 아쉬웠나 (사이트 기준)
- 사이트 `lib/blog-writer-prompts.js`(A/B/C 3전략)는 위 12패턴·8뱅크·16항목 **이전 버전**. 최신 홈판 패턴 미반영.
- 저품질 방지(도입 변주·리듬)·AEO 규칙이 사이트엔 약함.

### 1-3. 사이트로 이식할 레시피 층 (서버 프롬프트/로직)
- 제목 12패턴 + 결합공식 → 서버 프롬프트 규칙으로.
- 첫문장 8뱅크 + "배치 내 중복 금지" → 생성 파라미터로.
- 4단 구조 + 금지어 + AEO → 시스템 프롬프트.
- AI감지 16항목 → **별도 검수 패스**로(생성 프롬프트에 절대명령 쌓지 말 것 — rule-stacking 회피, 시즌2 방식과 동일).
- ※ wiki(06서사·07페르소나·08메시지)는 로컬 파일 → 사이트에선 **마이페이지 세팅(페르소나·자료 업로드)**으로 대체(시즌2 설계와 합침).

### 1-4. 로컬 전용 (사이트 불가 → PC 도우미/스킬 유지)
- 네이버 자동 발행(카무폭스, `naver_publisher.py`): 카테고리 자동선택·예약·이미지 삽입.
- 디스크 wiki/PDF 참고자료 직접 Read.

### 1-5. fable5 골드샘플 목록 (마감 창 생산 · 비교 아님 — 기준 문장 뱅크)
- 제목 12패턴 × 대표 업종 여러 개 → 골드 제목 뱅크.
- 첫문장 8뱅크 × 업종 → 골드 첫문장 뱅크(장면·대사 위주).
- ⚠️ 탈개인화(0-2c): 골드샘플도 특정인 실적 없이 "슬롯 자리" 형태로.

### 1-6. 🎯 목표 정렬 점검 (상위노출·홈판노출)
| 목표 | 블로그 생성기가 기여하는가 | 사이트가 못 하는(발행 몫) |
|---|---|---|
| 목적적합 | ✅ 유입/전환 키워드 2단 + 타겟 각도 고정 | — |
| 검색 상위 | ✅ 키워드 배치·정보완결·AEO·텍스트마이닝 반영 | 발행 분산(1.5~3h 간격)·카테고리 일관·내부링크·재발행 관리 → **PC 도우미** |
| 홈판 노출 | ✅ 제목 12패턴·첫3줄 훅·저품질 방지 도입변주 | 규칙 발행·주제 일관 축적(C-Rank)·실제 클릭/체류 반응 → **발행 전략 + 운영** |

**남은 구멍 (설계에 반영 필요):**
- (a) **채널 주제 일관성** = 상위노출·홈판 둘 다의 핵심인데 "글 한 편 생성"만으론 안 됨 → 사이트에 **주제 축(카테고리) 고정 + 발행 이력 관리**가 있어야. 단발 생성기론 부족.
- (b) **발행 규칙성·분산** = 저품질 회피의 핵심 → 사이트가 "예약 큐/분산 스케줄"까지 제안해야(생성만 X). 실제 발행은 PC 도우미.
- (c) **체류시간** = 정보 완결 + 이미지·표 + 내부링크. 이미지 생성기와 묶여야(Part 2 연계).
- (d) **반응(클릭·공감)** = 사이트가 직접 못 만듦. 제목·훅 품질로 확률만 올림 → 목표는 "노출 확률 최대화"로 정직하게 잡는다.

## Part 2. 이미지 생성기

### 2-1. 현재 자산 (사이트 blog-image-pro = 정교함)
- **타입별 모델 자동 라우팅**(Haiku가 마커 분석 → 타입·모델 배정):
  - `photo` → **fluxr(FLUX)**: 사실적 사진(감성·인물·제품·인테리어)
  - `infographic_data/flow · checklist · venn` → **satori**(코드 렌더 = 한글 정확·표/차트/흐름도)
  - `poster` → **nb2**
- 1번=썸네일, 본문 photo N장 + 정보이미지 혼합. R2 저장.

### 2-2. 갈림 (사이트 vs 스킬)
- 사이트: fluxr + satori + nb2 라우팅.
- 블로그 스킬(v2.3, 07-06): **satori 폐기 → gpt-image-2 high(썸네일 한글)·medium(본문)** 로 단순화.
- ⚠️ 이건 상충 아니라 **역할 분담으로 합치면 됨**(아래).

### 2-3. 🎯 목표 정렬 (이미지가 노출에 기여하는 길 2개)
| 목표 | 이미지 기여 | 어떤 이미지가 |
|---|---|---|
| 홈판 노출 | **썸네일 클릭률** | 한글 제목 들어간 썸네일(눈길). → gpt-image-2 high 또는 satori(한글 정확) |
| 검색 상위 | **체류시간 + 정보완결** | 표·차트·흐름도·체크리스트(스크롤 멈춤·이해). → satori(코드라 한글·수치 정확) |
| (공통) 성의 | 빈 화면·범용 커피컷 반복 금지 | 내용 담은 플랫 일러스트/정보이미지 |

### 2-4. 최종 스펙 (모델 역할 확정 — 갈림 해소)
- **썸네일(홈판 클릭)**: 한글 제목 텍스트 필요 → **gpt-image-2 high**(한글 안 깨짐) 우선. satori 템플릿도 가능(양자택일 A/B 검증은 이미지모델 비교).
- **정보 이미지(체류·상위노출)**: 표·차트·흐름도·체크리스트·벤 → **satori 유지**(코드 렌더라 한글·수치 100% 정확, 비용 0, 재현성 최고). ⚠️ 스킬이 satori 폐기했지만 **정보이미지는 satori가 맞다** — gpt-image류는 한글·표 부정확.
- **감성 사진(분위기 1~2장)**: **FLUX(fluxr)** 또는 gpt-image-2. "FLUX Option A" = 사진을 FLUX로 뽑는 선택 → 원가·품질로 결정(2-6).
- **금지**: 빈 UI·blank mockup, 범용 커피컷 반복.

### 2-5. 로컬 전용 / 사이트 몫
- 사이트 몫: 마커 분석·타입 라우팅·프롬프트·생성·R2 저장 = **전부 사이트에서 됨**(이미지는 서버 API라 로컬 불필요, 블로그와 달리 이식 쉬움).
- 로컬: 없음(스킬은 로컬 스크립트였지만 사이트가 이미 서버로 구현). ✅ 6종 중 이식 난도 가장 낮음.

### 2-6. fable5/모델 검증 포인트
- 썸네일: gpt-image-2 high vs satori 템플릿 클릭률 A/B(육안·후킹).
- 사진: FLUX(fluxr) vs gpt-image-2 원가·사실성 비교 → "FLUX Option A" 확정.
- (이미지 생성은 fable5(텍스트모델) 무관 — 이미지 전용 모델 비교임. fable5는 라우팅 판단 Haiku 자리 대체 검토만.)
## Part 3. 스레드 생성기

### 3-1. 현재 자산 (사이트 /api/threads = 꽤 성숙)
- **4유형**(정보형·공감형·반전형·궁금증형) × **말투**(친구체·격식체·단문체 등). 유형별 구조·첫문장 공식 내장.
- **바이럴 5요소**(생존관심사·댓글유발·공유유발·구체숫자·손실회피) 중 2개+ 강제.
- 500자 제한 + 어절 단위 trim(중간 절단 금지). `[답글]` 스레드 지원.
- 발행: **메타 공식 Threads API**(즉시·예약). OAuth 연동.

### 3-6. 🐞 알려진 결함 — 단문체 × 궁금증형(2단) 오류 (대표 제보)
**증상**: 단문체 + 궁금증형(이단구성) 조합이 늘 오류.
**원인(코드 진단 · route.js:239·50)**:
- 궁금증형은 본문(후킹→빌드업→끊기) + `[답글]` 구분자 + 답글의 **2단 필수**("[답글] 없으면 실패").
- 근데 그 조합만 **본문 100자 + 답글 50자**로 극단적으로 조임(line 240).
- 100자에 후킹·빌드업·끊기 + `[답글]`까지 못 담음 → 모델이 **`[답글]` 구분자 누락** → 답글 발행(`threads-publish-reply`)에 붙일 내용 없어 실패.
- 추가: 끊기 어미 충돌 — 단문체 "마침표로 끊기" vs 궁금증형 "`...`으로 끊기".
**수정 방향(구현 시)**:
1. 이 조합의 글자 예산 현실화: 본문 100→**140자**, 답글 50→**80자**(2단 유지 가능하게).
2. 끊기 규칙 충돌 해소: 궁금증형일 땐 "`...` 끊기"가 단문체 마침표 규칙보다 우선.
3. **출력 검증 게이트**: 궁금증형인데 `[답글]` 단독 줄 없으면 → 1회 자동 재생성, 그래도 없으면 정직하게 에러(빈 답글 발행 금지).
4. (대안) UI에서 단문체×궁금증형을 비권장 조합으로 안내.
⚠️ 완전 근본원인·재현은 실제 API 호출 필요 — 위는 코드 정독 기반 진단. 구현 단계에서 재현→수정→재현 검증.

- → "각각 따로 다듬기" 대신 **훅 엔진 1개 최고로 다듬어 6곳에 주입.** rule-stacking 회피 위해 검수는 별도 패스(시즌2 방식).
- **🔑 훅 엔진 = 프롬프트 + 회전/중복차단 레이어**(2026-07-07 실측 결론, `hook-engine-sonnet-prompt-v1.md`):
  - 프롬프트(v2, fable few-shot+하드제약) = **한 글 내 품질**(장면·다양성·금지어).
  - 시스템 레이어 = **글 간 다양성** — 패턴 회전(호출마다 조합 지정) + **사용자(계정)별** 최근 사용 blocklist(제목골격·숫자·장면). 독립 호출이라 프롬프트만으론 양산 단조를 못 막음(실측 확인).
  - ⚠️ blocklist는 반드시 사용자 단위로 격리 — 전역이면 A사용자의 표현이 B사용자를 막는 오작동(SaaS 탈개인화 0-2c와 같은 원리).
